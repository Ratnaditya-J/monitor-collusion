## Potential Concerns / Uncertainties

### 1. **RabbitMQ Subscription Pattern**
The broker config defines:
```
subscriptions: {
  audit_flush_worker: {
    queue: 'audit_flush_queue',
    prefetch: 1,
  },
}
```

But `audit-flush.ts` calls `broker.subscribe('audit_flush_worker')`. This assumes the Rascal library accepts subscription names as strings and internally maps them to queue names. Without library documentation, I cannot verify this pattern is correct or that it actually subscribes to `audit_flush_queue`.

### 2. **Immediate Flush Request in Scheduler**
In `scheduler.ts`, after processing deployments:
```
await publishAuditFlush();
```

This sends a flush request immediately after queuing the audit entries. This could create a race condition:
- Buffer entries are created
- Flush message is published
- Flush worker may run before all entries are fully committed

The audit service also has a count-based trigger:
```
if (pendingCount >= MAX_BUFFERED_AUDITS) {
  await publishAuditFlush();
}
```

Having both count-based and manual flush triggers could lead to duplicate flush attempts if timing coincides.

### 3. **Error Handling on Flush Failures**
If `flushDeploymentAuditBuffer()` fails partway through:
```typescript
await prisma.$transaction(async (tx) => {
  for (const entry of pending) {
    // Create audit log
  }
  await tx.deploymentAuditBuffer.deleteMany(...)
});
```

This uses a single transaction, so either all entries flush or none do. However, if the transaction fails, the entries remain in `DeploymentAuditBuffer` unflushed, potentially indefinitely until the next flush attempt. This is a design decision but worth noting.

### 4. **Missing `trigger` Field Handling**
The `DeploymentAuditBuffer` model includes a `trigger` column, but when creating `AuditLog` entries during flush, the `trigger` field is not included in the `AuditLog` table schema (see schema.prisma lines 94-107, no `trigger` field). The metadata includes the trigger type, which is correct.
